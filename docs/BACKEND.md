# 실제 신청 서비스로 전환하는 구성

현재 상태: 설계와 SQL 초안만 제공. 백엔드·DB·이메일 공급자 생성, SQL 실행, 실제 인증, DB 권한 통합 테스트는 수행하지 않았습니다. 본 문서는 운영 중인 인증 기능을 의미하지 않습니다.

## 권장 구성

| 계층 | 역할 | 공개 여부 |
|---|---|---|
| GitHub Pages | 화면·입력 폼·조회 UI | 공개 가능 |
| 별도 HTTPS API / BFF | 인증 시작·검증, 입력 검증, 본인 조회, 동의·삭제 처리 | 인증·권한 확인 후 접근 |
| Supabase Auth + SMTP | 짧은 수명의 이메일 OTP | 키·토큰은 서버 또는 검증된 인증 흐름에서 처리 |
| Supabase PostgreSQL | 신청 정보, 승인된 참가자, 동의 이력 | 비공개 DB, 행 단위 권한 |
| 운영자 전용 화면/API | 참가 자격 확인 및 수동 1:1 매칭 | 개별 운영자 계정 + MFA + 서버 권한 |

사내 이메일 OTP는 **해당 이메일함을 제어하는지** 확인하는 절차입니다. 이메일 주소 입력이나 도메인 검사만으로 재직·직무·임직원 신원을 보장하지 않습니다. 갤럭시 컨설턴트 자격은 회사에서 허용한 방식 또는 운영자가 승인한 참가 자격 검증으로 별도 확인해야 합니다. Knox SSO가 실제로 필요하면 회사의 승인·공식 연동 정보가 있어야 하며 현 코드에는 Knox 인증을 구현했다고 표시하지 않았습니다.

## 권장 사용자 흐름

1. 공개 홈 → 운영 안내와 개인정보 처리 안내 확인.
2. 서버가 허용한 사내 이메일 도메인인지 검사 → OTP 발송. 도메인 목록은 운영자가 검증한 실제 조직 도메인으로 서버에 설정. 예시 `samsung.com`을 전체 자격 증명으로 간주하지 않음.
3. OTP 검증 → 이메일 소유 확인 → 참가 자격 확인. 인증번호 만료, 일회성, 재전송·시도 횟수 제한, 사용자 존재 여부를 드러내지 않는 응답 필요.
4. 확인된 사용자 세션으로 신청서 제출. 서버가 모든 필드를 다시 검증하고 `owner_id`는 검증된 세션의 ID를 사용. 요청 본문에 사용자가 보낸 owner_id, role, verified, status는 거부.
5. 내 프로필 조회는 새로운 이메일 인증 또는 유효한 본인 세션으로 `GET /v1/me/application`. 이름·전화번호·이메일을 검색 키로 공개 조회하지 않음.
6. 운영자가 별도 접근 통제된 도구에서 조건을 검토. 상대에게 전달할 정보·연락처는 고지된 범위와 양쪽 동의를 확인한 뒤 최소한으로 공유.

## API 계약

| API | 필수 보호 | 응답 |
|---|---|---|
| POST /v1/auth/start | 도메인 정책, 이메일/IP별 제한, 동일한 일반 응답 | 발송 가능 여부를 노출하지 않는 202 |
| POST /v1/auth/verify | 만료·횟수 제한·재사용 방지 | 인증된 세션 또는 일반화된 오류 |
| GET /v1/me | 서버 세션 검증 | 본인 상태·참가 자격 상태만 |
| POST /v1/me/application | 인증+참가 자격+동의, 본문 스키마 검증, 중복 방지 | 실제 커밋 후만 201과 신청 ID |
| GET /v1/me/application | 본인 권한 | 본인 신청서 또는 404 |
| PATCH /v1/me/application | 본인 권한, 변경 가능한 필드만 | 수정 완료 |
| DELETE /v1/me/application | 재인증 및 본인 권한 | 삭제 완료 204 |
| POST /v1/auth/logout | 세션 무효화 | 204 |

본문 필드는 현재 `index.html`의 `name` 값과 대응합니다. `preferredRegions`와 `charms`는 배열로 전달하고 모든 문자열은 길이 제한, 공백 검증을 수행합니다. MBTI·성별·지역·데이트 선택지는 허용 목록으로 검증하고, 출생연도·운영 대상 연령 정책도 서버에서 검증합니다. 실패 시 사용자 입력을 URL·로그·에러 추적 도구에 노출하지 않습니다.

## DB 권한

`backend/001_schema.sql`은 Supabase용 시작점입니다. 새 테스트 프로젝트에서 검토 후 적용하세요.

- 참가자 테이블과 프로필 테이블 모두 RLS 활성화·강제 적용.
- anon 및 일반 공개 역할 권한 철회.
- 인증 사용자는 본인 행만 조회·수정·삭제.
- 참가 자격 부여는 사용자에게 허용하지 않으며 서버의 별도 승인 절차만 사용.
- 신청 저장·수정은 승인된 참가자에게만 허용.
- service_role 같은 우회 권한 키는 **서버 비밀 저장소 전용**. 프론트엔드에 포함하지 않음.
- API는 검증된 사용자 JWT의 권한으로 DB 접근하는 것을 기본으로 함. service_role로 일반 요청을 대리할 경우 RLS가 우회되므로 매 요청의 본인 권한을 서버에서 별도 강제해야 함.
- 매칭 상태·상대 정보는 참가자가 수정하는 프로필 테이블에 추가하지 말고 서버 전용 테이블로 분리.

## 세션과 배포

페이지를 공개해도 데이터 API는 인증을 요구합니다. 같은 운영 도메인의 `www`와 `api` 서브도메인을 사용하는 구성을 권장합니다. API 세션 쿠키는 Secure·HttpOnly·적절한 SameSite, CSRF 방어를 적용합니다. `github.io`와 다른 도메인의 API는 쿠키 제한과 CORS를 별도로 검토해야 합니다. CORS만으로 인증을 대체하지 않습니다.

API, DB, SMTP 키는 각각 서버 환경 변수·비밀 저장소에 둡니다. GitHub Actions에도 신청자 데이터나 DB 관리자 키를 넣지 않습니다. 정식 전환 시 CSP의 `connect-src 'none'`은 검증된 API 출처만 허용하도록 바꾸고 나머지 외부 출처는 계속 제한합니다. 토큰·신청 내용을 localStorage에 보관하지 않습니다.

## 운영 전 실제로 결정·구현할 항목

- 운영 책임자·문의처, 수집 항목·목적·보관 기간·삭제·철회 절차와 동의 문구
- 참가 연령·자격 기준, 재직 확인 방식, 이메일 수신 가능 여부
- 전송 암호화·저장 암호화, 필요한 경우 연락처 필드 암호화와 키 분리
- 로그에서 개인정보 제거, 운영자 MFA·최소 권한·접근 감사, 백업 접근 통제
- 만료 데이터 자동 삭제 작업 및 백업 보관 정책
- 비인증 사용자 접근 차단, A 사용자가 B의 UUID로 조회·수정·삭제할 수 없는지 통합 테스트
- OTP 재사용·무차별 시도 차단, DB 실패·중복 제출·삭제 실패 테스트
- 실제 저장 성공을 확인한 뒤에만 '신청 접수 완료' 표시. 인증 실패 시 신청·조회 모두 차단.

개인정보 관련 실제 운영 요건은 운영 주체와 이용 방식에 맞춰 검토해야 합니다. 이 초안만으로 운영 준비가 완료된 것은 아닙니다.
